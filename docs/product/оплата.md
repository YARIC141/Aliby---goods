## 1. Два независимых платёжных потока

Платформа содержит **два принципиально разных вида оплаты**:

| Поток | Кто платит | Кому | Эквайринг | Таблицы |
|-------|-----------|------|-----------|---------|
| **Платформенная подписка** | Продавец | ИП Копылов (Alliby) | T-Bank терминал Alliby | `platform_subscriptions` |
| **Клиентский абонемент** | Покупатель | Продавец | T-Bank терминал Продавца | `subscriptions`, `user_subscriptions`, `payments` |

Деньги за клиентские абонементы **не проходят через Alliby** — они уходят напрямую на счёт Продавца через его собственный терминал эквайринга.

## 2. Таблицы БД

### 2.1. `platform_subscriptions` — подписки продавца на платформу

```sql
id                      UUID PRIMARY KEY
user_id                 UUID → auth.users
store_id                UUID → stores   -- NULL = платформенная, NOT NULL = слот под доп. заведение
plan                    TEXT            -- 'monthly' | 'yearly'
plan_type               TEXT            -- 'platform' | 'store'
status                  TEXT            -- 'pending' | 'active' | 'grace' | 'cancelled' | 'expired' | 'failed'
start_date              DATE
end_date                DATE
amount_paid             INTEGER         -- рублей
is_trial                BOOLEAN DEFAULT false
auto_renew              BOOLEAN DEFAULT true
rebill_id               TEXT            -- RebillId от T-Bank (нужен для рекуррентных списаний)
tbank_payment_id        TEXT UNIQUE     -- PaymentId от T-Bank (для матчинга вебхуков)
monthly_amount_kopecks  INTEGER DEFAULT 100000  -- сумма следующего автосписания в копейках
retry_count             INTEGER DEFAULT 0       -- счётчик неудачных попыток продления
grace_until             DATE
created_at              TIMESTAMPTZ
```

**SQL-функции на уровне БД:**

- `user_store_limit(p_user_id)` → `1 + COUNT(active store-type subs)` — сколько заведений может иметь пользователь; базовый бесплатный лимит = 1.
- `is_store_subscription_active(p_store_id)` → `true/false` — есть ли у владельца активная platform-подписка (`status IN ('active','grace')`, `end_date >= today`).
- `sync_store_visibility()` — триггер AFTER UPDATE на `platform_subscriptions`: при `plan_type='store'` и `status='expired'/'cancelled'` → заведению `is_visible = false`; при `status='active'/'grace'` → `is_visible = true`.
- `check_store_limit()` — триггер BEFORE INSERT на `stores`: выбрасывает `store_limit_reached` если лимит исчерпан.

### 2.2. `subscriptions` — шаблоны абонементов (продавец создаёт)

```sql
id              UUID PRIMARY KEY
store_id        UUID → stores
name            TEXT
price           NUMERIC(10,2)
duration_days   INTEGER
total_uses      INTEGER DEFAULT 0   -- 0 = безлимит
items_per_use   INTEGER DEFAULT 1
coverage_rules  JSONB  -- { type: 'all'|'include_categories'|'include_items'|'exclude_items', ... }
time_rules      JSONB  -- { weekdays:[1-7], time_start:"HH:MM", time_end:"HH:MM", excluded_dates:[] }
usage_limits    JSONB  -- { daily_limit:N, min_interval_hours:N, min_order_amount:N }
discount_type   TEXT   -- 'percent' | 'fixed'
discount_value  NUMERIC(10,2)
stock_total     INTEGER NULL  -- NULL = безлимит
stock_sold      INTEGER DEFAULT 0
```

Триггер `trg_sub_stock` (BEFORE INSERT на `user_subscriptions`) атомарно инкрементирует `stock_sold`, выбрасывает `out_of_stock` при исчерпании лимита.

### 2.3. `user_subscriptions` — купленные покупателями абонементы

```sql
id                  UUID PRIMARY KEY
user_id             UUID → profiles
subscription_id     UUID → subscriptions
status              TEXT   -- 'pending' | 'active' | 'expired' | 'cancelled'
purchase_date       TIMESTAMPTZ
start_date          TIMESTAMPTZ
end_date            TIMESTAMPTZ
remaining_uses      INTEGER NULL   -- NULL = безлимит
used_today          INTEGER DEFAULT 0
last_used_at        TIMESTAMPTZ
gift_status         TEXT NULL      -- 'pending' | 'activated'
```

### 2.4. `payments` — записи об оплатах клиентских абонементов

```sql
id                      UUID PRIMARY KEY
order_id                UUID → orders   -- EXCLUSIVE OR с user_subscription_id
user_subscription_id    UUID → user_subscriptions
amount                  NUMERIC(10,2)
status                  TEXT            -- 'pending' | 'succeeded' | 'cancelled' | 'failed'
provider_transaction_id TEXT UNIQUE     -- PaymentId T-Bank
metadata                JSONB           -- { is_gift, store_id, additional_user_sub_ids:[] }
```

Constraint `payment_target_check` гарантирует: ровно одно из полей (`order_id` или `user_subscription_id`) не NULL.

### 2.5. `user_payment_settings` — зашифрованные ключи эквайринга продавца

```sql
user_id            UUID PRIMARY KEY → auth.users
terminal_key       TEXT   -- AES-GCM зашифрован (боевой режим)
secret_key         TEXT   -- AES-GCM зашифрован (боевой режим)
terminal_key_test  TEXT   -- тестовый терминал
secret_key_test    TEXT   -- тестовый терминал
key_version        INT DEFAULT 1
updated_at         TIMESTAMPTZ
```

Таблица без RLS — доступна только через `service_role`. Ключи шифруются через AES-GCM (`_shared/payment-crypto.ts`) перед записью.

### 2.6. `subscription_consents` — согласия на рекуррентные списания

```sql
id            UUID PRIMARY KEY
user_id       UUID → auth.users
ip_address    TEXT
user_agent    TEXT
consent_text  TEXT
created_at    TIMESTAMPTZ
```

## 3. Тарифы

### Платформенная подписка (продавец → Alliby)

| Тип | Сумма | Период | Примечание |
|-----|-------|--------|------------|
| **Пробный период (trial)** | 1 ₽ | 30 дней | Рубль сразу возвращается через `/v2/Cancel`; нужен только для привязки карты и получения `RebillId` |
| **Основная подписка** | 1 000 ₽/мес | 30 дней | Рекуррентно через `RebillId`; активируется после trial |
| **Доп. заведение (monthly)** | 500 ₽/мес | 30 дней | `plan_type='store'`; рекуррентно |
| **Доп. заведение (yearly)** | 5 000 ₽/год | 365 дней | `plan_type='store'`; экономия 1 000 ₽ vs 12×500 |

Суммы константами в `tbank-platform-init/index.ts`:
```ts
const TRIAL_AMOUNT_KOPECKS       = 100     // 1 ₽
const ADD_STORE_MONTHLY_KOPECKS  = 50000   // 500 ₽
const ADD_STORE_YEARLY_KOPECKS   = 500000  // 5 000 ₽
// Основная: monthly_amount_kopecks = 100000 (1 000 ₽) хранится в БД
```

### Абонементы клиентов

Продавец настраивает самостоятельно: цена, длительность, число визитов, покрытие, лимиты использования. Платформа не фиксирует тариф — только проводит платёж через эквайринг продавца.

## 4. Платформенная подписка продавца

### 4.1. Prerequisite: договор

Перед началом оплаты вызывается `requireContract('seller', callback)`. Если Лицензионный договор не подписан — показывается форма ПЭП. Подпись сохраняется в `contract_signatures`. Без подписанного договора инициация платежа невозможна.

### 4.2. Полный поток: trial → active

```
1. Продавец: нажимает "Начать бесплатный месяц"
   UI: startPlatformSubscription() → requireContract() → openModal('m-platsub-plans')

2. Продавец: ставит галочку согласия → нажимает "Начать бесплатный месяц →"
   UI: initTrialPayment()

3. POST /functions/v1/tbank-platform-init  { type: 'trial', consent_given: true }
   Edge Function:
   ├─ Проверяет роль 'admin'
   ├─ Проверяет: нет активной/grace платформенной подписки
   ├─ Делает стale все 'pending' записи (status → 'failed')
   ├─ INSERT platform_subscriptions:
   │    status='pending', plan='monthly', plan_type='platform',
   │    is_trial=true, amount_paid=0, monthly_amount_kopecks=100000,
   │    end_date=today+30
   ├─ POST T-Bank /v2/Init: Amount=100 (1 ₽), Recurrent='Y', CustomerKey=user.id
   ├─ Сохраняет tbank_payment_id
   ├─ INSERT subscription_consents (если consent_given=true)
   └─ Возвращает { payment_url, payment_id, subscription_id }

4. Браузер: редирект на payment_url (страница T-Bank)

5. Продавец: вводит карту, подтверждает 1 ₽

6. T-Bank → POST /functions/v1/tbank-platform-notify
   Edge Function (вебхук):
   ├─ Верифицирует HMAC-токен (SHA-256 + TBANK_PASSWORD)
   ├─ Находит platform_subscriptions по tbank_payment_id = PaymentId
   ├─ Status='CONFIRMED' && Success=true:
   │    UPDATE: status='active', rebill_id=RebillId
   │    Асинхронно: POST /v2/Cancel (Amount=100) — возврат 1 ₽
   │    Логирует аналитику
   └─ Status IN (REJECTED, CANCELLED, DEADLINE_EXPIRED):
        UPDATE: status='failed'

7. Браузер: T-Bank редиректит на admin.alliby.ru/?tpay=success (или ?tpay=fail)
   UI:
   ├─ tpay=success → зелёный баннер + _pollForActiveSub(8 попыток × 2 сек)
   │   опрашивает platform_subscriptions до status='active'
   └─ tpay=fail → красный баннер "Оплата не завершена"
```

### 4.3. Состояния подписки

```
pending  →  active (вебхук CONFIRMED)
pending  →  failed (вебхук REJECTED/CANCELLED)
active   →  grace  (автосписание неуспешно, retry_count < 3)
active   →  cancelled (продавец нажал "Отменить")
grace    →  active (повторное автосписание успешно)
grace    →  expired (retry_count >= 3)
```

При `status IN ('active', 'grace')` подписка считается **активной** — все функции работают, клиенты могут платить.

## 5. Автоплатёж и продление

### 5.1. Cron-задание

`tbank-platform-charge` запускается ежедневно (pg_cron или внешний планировщик, `Authorization: Bearer CRON_SECRET`). Находит подписки где `end_date <= today, status IN ('active','grace'), auto_renew=true, rebill_id IS NOT NULL`.

### 5.2. Логика продления

```
Для каждой подписки:

  retry_count >= 3?
    → status='expired'; пропустить

  POST /v2/Init { Amount=monthly_amount_kopecks, без SuccessURL }
  POST /v2/Charge { PaymentId, RebillId }

  Успешно (CONFIRMED):
    end_date += 30 дней (от старого end_date, не от сегодня)
    status='active', retry_count=0, grace_until=null, is_trial=false
    amount_paid = amount/100

  Неуспешно:
    retry_count++
    retry_count >= 3 → status='expired'
    retry_count < 3  → status='grace', grace_until = today + (3-retry_count) дней
```

### 5.3. Уведомление за 3 дня

`tbank-platform-notify-email` ежедневно в 07:00 UTC: находит подписки с `end_date = today+3, auto_renew=true, rebill_id IS NOT NULL` → отправляет email через SMTP. Позволяет продавцу обновить карту до автосписания.

### 5.4. Управление автоплатежом из UI

```js
// Отключить автоплатёж (подписка истечёт, но не продлится)
PATCH platform_subscriptions { auto_renew: false }

// Отменить подписку немедленно (при is_trial=true — спрашивает подтверждение)
PATCH platform_subscriptions { status: 'cancelled' }
// Доступ сохраняется до end_date; cron игнорирует status='cancelled'
```

## 6. Дополнительное заведение

### 6.1. Prerequisite

Основная platform-подписка (`plan_type='platform'`, `status='active'/'grace'`) **обязательна**. Без неё:
- UI: `onAddStoreBtnClick()` → `!_activePlatSub` → модал «Нужна основная подписка»
- БД: `user_store_limit()` = 1 (бесплатный лимит без платформенной подписки)
- Триггер `check_store_limit()` заблокирует INSERT в `stores`

### 6.2. Поток оплаты доп. заведения

```
1. Продавец: нажимает "Добавить заведение" → openModal('m-add-store-plan')

2. Выбирает тариф (monthly 500₽ / yearly 5 000₽)
   UI: selectAddStorePlan(plan) → openModal('m-add-store-pay')

3. Продавец: нажимает "Оплатить"
   POST /functions/v1/tbank-platform-init {
     type: 'add_store',
     plan: 'monthly' | 'yearly',
     store_id: null  -- если заведение ещё не создано
   }

   Edge Function:
   ├─ Проверяет активную platform-подписку (plan_type='platform')
   ├─ Делает stale все 'pending' store-подписки
   ├─ INSERT platform_subscriptions:
   │    plan_type='store', plan='monthly'/'yearly', status='pending',
   │    store_id=null, monthly_amount_kopecks=50000/500000,
   │    amount_paid=500/5000, auto_renew=true
   ├─ POST T-Bank /v2/Init: Amount=50000/500000, Recurrent='Y'
   └─ Возвращает payment_url

4. Вебхук CONFIRMED → status='active', rebill_id сохранён

5. После создания нового заведения (saveStore()):
   ├─ GET platform_subscriptions (plan_type='store', store_id IS NULL, active/grace)
   └─ PATCH platform_subscriptions { store_id: newStoreId }
      Слот привязывается к заведению
```

### 6.3. Лимиты

```
user_store_limit(user_id) = 1 + COUNT(active store-subs)

Примеры:
  0 store-subs → лимит 1 (1 бесплатное заведение)
  1 store-sub  → лимит 2 (1 бесплатное + 1 за monthly 500₽)
  2 store-subs → лимит 3 (1 бесплатное + 2 платных)
```

### 6.4. Связь видимости заведения со статусом store-подписки

Триггер `sync_store_visibility()` срабатывает при UPDATE `platform_subscriptions`:

| status (store-sub) | stores.is_visible |
|--------------------|------------------|
| `active` / `grace` | `true` |
| `expired` / `cancelled` | `false` |

Заведение автоматически **пропадает с карты** при истечении/отмене store-подписки.

## 7. Клиентский абонемент

Деньги проходят через **эквайринг Продавца**. Платформа выступает только как процессинговый посредник — получает ключи продавца, инициирует платёж от его имени.

### 7.1. Настройка эквайринга продавца

```
1. Продавец вводит ключи T-Bank терминала в admin-панели
2. POST /functions/v1/payment-settings-set
   ├─ Шифрует terminal_key + secret_key через AES-GCM (ключ ENCRYPTION_KEY из env)
   └─ UPSERT user_payment_settings
```

### 7.2. Покупка абонемента (клиент)

```
1. Клиент выбирает абонемент в приложении
   POST /functions/v1/tbank-init-sub {
     subscription_ids: ['uuid', ...],
     is_gift: false
   }

   Edge Function:
   ├─ Проверяет наличие активной platform_subscriptions у продавца (403 иначе)
   ├─ Читает user_payment_settings продавца, расшифровывает ключи
   ├─ INSERT user_subscriptions (status='pending') для каждого subscription_id
   │    Триггер trg_sub_stock: stock_sold++ (выброс out_of_stock → вся транзакция откатится)
   ├─ INSERT payments (status='pending', metadata={store_id, additional_sub_ids})
   ├─ POST T-Bank /v2/Init с ключами ПРОДАВЦА
   └─ Возвращает payment_url

2. Клиент: вводит карту, подтверждает оплату

3. T-Bank → POST /functions/v1/tbank-sub-notify
   CONFIRMED/AUTHORIZED:
     payments.status = 'succeeded'
     user_subscriptions.status = 'active' (все: primary + additional)
   REJECTED/CANCELLED/DEADLINE_EXPIRED:
     payments.status = 'failed'/'cancelled'
     user_subscriptions.status = 'cancelled'
```

### 7.3. Подарочный абонемент

- При `is_gift=true`: `user_subscriptions.gift_status='pending'` — абонемент ждёт активации.
- Получатель вызывает `activate_gift_subscription(p_gift_sub_id)`:
  - Атомарно создаёт копию `user_subscriptions` под получателем
  - Помечает оригинал `gift_status='activated'`
  - Нельзя активировать свой же подарок (ошибка `self_activation`)

## 8. Списание по абонементу

### 8.1. Валидация

```
POST /functions/v1/validate-subscription {
  user_subscription_id,
  order_items: [{ menu_item_id, quantity }]
}
```

Проверяет (все условия в AND):
- `status='active'`, `end_date >= now()`
- `remaining_uses > 0` (или NULL — безлимит)
- `used_today < daily_limit` (если задан)
- `last_used_at < now() - min_interval_hours` (если задан)
- `coverage_rules`: входят ли товары заказа в покрытие абонемента
- `time_rules`: текущее время и день недели в разрешённом диапазоне, дата не в `excluded_dates`
- `min_order_amount` выполнен

Возвращает `{ valid: true, discount_amount: N }` или `{ valid: false, reason: '...' }`.

### 8.2. Атомарное списание

```
POST /functions/v1/redeem-subscription {
  user_subscription_id, order_id, amount_discounted
}

Вызывает SQL-функцию redeem_subscription() (SELECT FOR UPDATE, транзакция):
  ├─ Повторная проверка: статус, срок, remaining_uses, used_today, last_used_at
  ├─ Сбрасывает used_today = 0 если last_used_at < начало сегодня (UTC)
  ├─ remaining_uses-- (если не NULL)
  ├─ used_today++, last_used_at = now()
  ├─ INSERT subscription_redemptions (history)
  └─ UPDATE orders: applied_user_subscription_id, subscription_discount,
       status='paid', payment_method='subscription'
```

SELECT FOR UPDATE предотвращает двойное списание при параллельных запросах.

## 9. Корнер-кейсы

### 9.1. Оплата не прошла — платформенная подписка

**Вебхук `REJECTED`/`CANCELLED`/`DEADLINE_EXPIRED`:**
- `platform_subscriptions.status = 'failed'`
- T-Bank редиректит на `?tpay=fail` → красный баннер
- Продавец может повторить попытку: при новой инициации все старые `pending` записи переводятся в `failed`

### 9.2. Оплата не прошла — клиентский абонемент

- `payments.status = 'failed'`
- Все `user_subscriptions.status = 'cancelled'`
- `stock_sold` не декрементируется (запись `user_subscriptions` уже создана, триггер уже отработал). Фактически — потеря одного слота стока. При необходимости корректируется вручную.

### 9.3. Вебхук не пришёл / упал (платформенная подписка)

- `platform_subscriptions.status` остаётся `'pending'`
- При повторной попытке оплаты: все `pending` записи переводятся в `failed`, создаётся новая
- `_pollForActiveSub()` опрашивает 8 раз × 2 сек = 16 сек, затем просит обновить страницу

### 9.4. Подписка продавца истекает (platform)

- `is_store_subscription_active(store_id)` → false
- `tbank-init-sub` возвращает `403 "Store is temporarily unavailable"` — клиенты не могут купить абонемент
- Заведение **остаётся видимым** — только клиентские платежи заблокированы
- Admin-UI: badge "Подписка истекла" + кнопка продления

### 9.5. Store-подписка истекает (доп. заведение)

- Триггер `sync_store_visibility()` → `stores.is_visible = false`
- Заведение **исчезает с карты** клиентского приложения
- Admin-UI: badge "Истекла" на заведении + предложение продлить
- При продлении (новый платёж, `status → active`) — триггер возвращает `is_visible = true`

### 9.6. Автоплатёж неуспешен — grace-период

```
retry_count=1 → grace, повтор завтра
retry_count=2 → grace, повтор послезавтра
retry_count=3 → expired (функции отключаются)
```

- В статусе `grace` подписка **считается активной** — все функции работают
- Email-уведомление отправляется при каждой неудачной попытке
- Продавец может вручную обновить карту: нет механизма прямой смены карты в текущей реализации (нужен новый платёж)

### 9.7. Продавец отменяет подписку

- `PATCH platform_subscriptions { status: 'cancelled' }`
- Доступ **сохраняется до `end_date`** — `is_store_subscription_active` проверяет `end_date >= CURRENT_DATE`
- Cron игнорирует `status='cancelled'` — списания не будет
- `auto_renew` не имеет значения при `status='cancelled'`

### 9.8. Попытка создать заведение без платформенной подписки

- UI: `saveStore()` → `!_activePlatSub` → перенаправляет на `startPlatformSubscription()`
- БД: `user_store_limit()` = 1; если одно заведение уже есть → триггер `check_store_limit()` выбрасывает `store_limit_reached`

### 9.9. Добавить заведение без store-подписки

- UI: `onAddStoreBtnClick()` → `!_activePlatSub` → модал "Нужна основная подписка"
- Если основная есть, но store-слотов нет → предлагается купить store-подписку
- `user_store_limit()` = 1 без store-слотов → триггер заблокирует второе заведение даже при прямом SQL

### 9.10. Сток абонемента исчерпан

- Триггер `trg_sub_stock` (BEFORE INSERT `user_subscriptions`): `stock_sold >= stock_total` → выброс `out_of_stock`
- Вся транзакция в `tbank-init-sub` откатывается: `user_subscriptions` не создаются, `payments` не создаётся
- Edge Function возвращает 409 "Out of stock"
- UI показывает ошибку клиенту

### 9.11. Параллельные списания по одному абонементу

- `redeem_subscription()` использует `SELECT FOR UPDATE` на строке `user_subscriptions`
- Второй параллельный запрос ждёт снятия блокировки, затем видит обновлённый `remaining_uses`
- Двойное списание невозможно

### 9.12. Задвоенные store-слоты (store_id = NULL)

- Может возникнуть при прерванном потоке (оплатил, но не создал заведение)
- Слоты с `store_id=NULL` и `status='active'` — незадействованный оплаченный лимит
- При создании заведения: система берёт первый свободный слот и привязывает
- Если свободных слотов нет несмотря на оплату — UI предложит новую покупку (граничный случай)

### 9.13. Yearly store-подписка и автоплатёж

- `monthly_amount_kopecks = 500000` (5 000 ₽)
- `auto_renew=true` → через 365 дней cron попытается списать 5 000 ₽ через `rebill_id`
- Если продавец хочет перейти на monthly — нет UI для downgrade; только отменить yearly и купить monthly после истечения
